Signadot trial report

Signadot gives every change its own lightweight sandbox inside one shared Kubernetes cluster. A sandbox runs only the services you changed. Requests that carry its routing key go to those services, and everything else uses the shared baseline, so you test against real dependencies without copying the whole stack.

The demo app: HotROD

HotROD is a small ride-sharing app made of four services. Booking a ride sends one request through all of them, which makes it easy to see which version of each service handled it.

The browser shows each step as a notification, ending with "Driver T7… arriving in N min". Every notification records which service handled it and whether a sandbox did, which is how each card below proves where a request went.

What adopting this would take for your team

Header propagation

Services pass the routing key along with each request, usually through OpenTelemetry baggage, which many teams already propagate. How

Request routing

Signadot DevMesh (a lightweight sidecar), Istio or Linkerd sends keyed requests to sandboxes. Options

Queue consumers

Consumers of Kafka, RabbitMQ, Redis Streams, Temporal and similar systems check the routing key, so sandboxes and baseline each process only their own messages. Patterns

Database strategy

Shared databases, per-sandbox databases from resource plugins, or a mix, depending on what each change touches. Strategies

Operator and CLI

One Helm-installed operator per cluster, and the Signadot CLI or a CI integration to create sandboxes from pull requests. Install
