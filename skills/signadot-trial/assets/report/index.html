Signadot trial

Signadot gives every change its own lightweight sandbox inside one shared Kubernetes cluster. A sandbox runs only the services you changed. Requests that carry its routing key go to those services, and everything else uses the shared baseline, so you test against real dependencies without copying the whole stack. Each scenario below has its own page with what was tested, the proof, and what it means for your team.

Scenarios

The demo app: HotROD

HotROD is a small ride-sharing app made of four services. Booking a ride sends one request through all of them, and each step records which version of the service handled it, which is how the scenarios prove where a request went.

What's running now

Look at the cluster yourself

The trial keeps the cluster's credentials in its own kubeconfig, inside the trial folder, so your current kube context is unchanged and tools like kubectx don't list the trial's cluster. Point any terminal at it:

export KUBECONFIG="TRIAL_FOLDER/kubeconfig"
kubectl config current-context    # kind-signadot-trial
kubectl -n hotrod get pods        # the demo app, with each sandbox's pod next to the normal ones
kubectl -n signadot get pods      # Signadot's operator

With that variable set, kubectx, k9s, Lens and other Kubernetes tools see the cluster too. To add it to your own kubeconfig instead, run kind export kubeconfig --name signadot-trial; note that this also switches your current context to kind-signadot-trial.

Sandboxes, route groups and test runs are also in the Signadot dashboard: app.signadot.com.

What adopting Signadot would take

Header propagation

Services pass the routing key along with each request, usually through OpenTelemetry baggage, which many teams already propagate. How

Request routing

Signadot's own lightweight sidecar, Istio or Linkerd sends keyed requests to sandboxes. Options

Queue consumers

Consumers of Kafka, RabbitMQ, Redis Streams, Temporal and similar systems check the routing key, so sandboxes and baseline each process only their own messages. Patterns

Database strategy

Shared databases, per-sandbox databases from resource plugins, or a mix, depending on what each change touches. Strategies

Operator and CLI

One Helm-installed operator per cluster, and the Signadot CLI or a CI integration to create sandboxes from pull requests. Install
